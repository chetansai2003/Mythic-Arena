# Part 2 REST and security contract

All paths below are API-relative. The browser uses `/api` through the Vite proxy. Authentication and deck mutation errors use `{ error: { code, message, requestId, details? } }`. Validation details identify fields without logging raw credentials.

## Identity and sessions

| Method/path           | Request                            | Result                                            |
| --------------------- | ---------------------------------- | ------------------------------------------------- |
| GET `/auth/csrf`      | Same-origin browser request        | `{ csrfToken }` and a signed httpOnly CSRF cookie |
| POST `/auth/register` | `{ email, displayName, password }` | 201 profile, access token, expiry; refresh cookie |
| POST `/auth/login`    | `{ email, password }`              | 200 profile, access token, expiry; refresh cookie |
| POST `/auth/refresh`  | Refresh cookie and CSRF header     | Rotated refresh cookie, new access token/profile  |
| POST `/auth/logout`   | Refresh cookie and CSRF header     | 204, durable family revocation, cleared cookies   |
| GET `/auth/me`        | Bearer access token                | `{ user: { id, email, displayName, createdAt } }` |

Email is trimmed, lowercased, validated, and uniquely indexed. Display names contain 2–40 characters. Registration passwords contain 12–128 characters; passwords are not trimmed. Argon2id uses 19 MiB memory, two iterations, and parallelism one. Invalid credentials have the same response for existing and unknown accounts.

Access tokens are HS256 JWTs with issuer `mythic-arena`, audience `mythic-web`, a user subject, and session-family ID. Default lifetime is ten minutes. Every protected request verifies the signature, expiry, and the active family in MongoDB. Tokens live in Redux memory only. Preferences and non-secret draft/selection data are the only browser-persisted state.

Refresh credentials are 48 random bytes encoded as base64url. MongoDB stores only their SHA-256 hashes. Families have an absolute seven-day expiry by default; refresh does not extend it. A MongoDB transaction consumes the old credential and creates its replacement. Reuse of a consumed token revokes the entire family, including its access tokens. Logout also revokes the family immediately. An injectable `onSessionRevoked` hook is ready for Part 4 socket termination; there are no sockets to close in Part 2.

Production cookie names use `__Host-`, Secure, HttpOnly, Path=/, SameSite=Strict, and no Domain. Local HTTP uses non-prefixed cookies with Secure disabled. Production configuration rejects HTTP frontend origins. Refresh/logout and other mutations require both an explicitly allowed Origin and a valid signed CSRF cookie echoed in `x-csrf-token`; the cookie itself is httpOnly. Secrets are generated by `npm run setup`, excluded from source control/build context, and never printed.

Redis applies per-minute registration, login-IP, login-email, refresh, and CSRF limits. Login email/IP values are hashed in rate-limit keys. Counters are atomic and expire. Redis failure rejects throttled account requests rather than silently disabling protection. Known proxy addresses are not automatically trusted from caller headers.

The browser coalesces concurrent refreshes and uses the Web Locks API when available to serialize refresh/sign-in/logout operations. Sign-in waits for initial session restoration, preventing a late guest response from discarding the new login. Use separate browser profiles or private windows for simultaneous different accounts.

## Cards and decks

| Method/path         | Request                                                  | Result                                                                 |
| ------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------- |
| GET `/cards`        | Public read                                              | Versioned definitions, rules/catalog versions, and battle availability |
| GET `/decks`        | Bearer access token                                      | Only the authenticated user's saved decks                              |
| POST `/decks`       | `{ name, cardIds }`, bearer and CSRF                     | 201 saved deck, revision 1                                             |
| PATCH `/decks/:id`  | `{ name?, cardIds?, expectedRevision }`, bearer and CSRF | Updated deck with incremented revision                                 |
| DELETE `/decks/:id` | `{ expectedRevision }`, bearer and CSRF                  | 204 only for the current owned revision                                |

Saved decks require exactly 30 known card IDs, at most two of each. All 20 seeded definitions are available to every account. Ownership comes from the authenticated subject, never from request data. Cross-account update/delete returns 404. Revision conflicts return 409 with edits preserved in the UI. Incomplete decks are local drafts; they are not persisted as valid server decks.

The seed is explicit and idempotent. Index creation and 20 versioned definitions complete before the schema-ready marker is written. Existing version-1 card definitions are immutable; a changed definition requires a new version. The initializer does not create users or overwrite user decks. Compose runs this as a separate one-shot service before the API starts.

Each card has declared finite behavior and a nullable artwork reference; faction artwork is an original SVG/CSS fallback. As of Step 3 the engine implements DAMAGE, HEAL, SHIELD, and GUARD. `valid: true` means deck composition is valid; `playable: true` means the engine supports it for practice. It does not imply online matchmaking is available.

The internal `snapshotForMatch` helper freezes rules/catalog/deck versions and definitions and assigns a distinct instance ID to each card occurrence. Once created, that snapshot's IDs remain stable and later deck edits do not change it. Part 3/4 must use it once at match creation and enforce engine readiness; Part 2 exposes no match-start endpoint.

## Editor recovery

Save failures retain the current draft. Unsaved navigation prompts before leaving; browser unload prompts while dirty. A validated draft is stored in sessionStorage under the account ID where storage is available, allowing restoration after reload or sign-in. Preferences/selected deck IDs use localStorage; no passwords or tokens do. Storage failure falls back to the current in-memory draft. Deletion requires a dialog confirmation and server revision check. Concurrent-save conflicts offer reload or save-as-copy without overwriting the other revision.
